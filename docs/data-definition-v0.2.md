# RAGポートフォリオ データ定義書 v0.2

作成日: 2026-08-04
PM: クリーデ
対応要件定義: 統合定義書 v0.3

## チャンクレコード（共通・Chroma格納単位）

| フィールド | 型 | 内容 |
|---|---|---|
| chunk_id | str | `{doc_slug}-{連番}` |
| doc_type | str | `spec`（仕様書条文）/ `form`（帳票・v1.1） |
| hierarchy | str | 条文は階層パス（例：`第3編/第2章/第1節/3-2-1-2`）、帳票は`{帳票名}/{表番号}` |
| heading | str | 見出しテキスト。埋め込み対象はheading＋body連結 |
| body | str | 本文または表（Markdown表として整形） |
| pages | str | 元PDFのページ範囲（例：`45-46`） |
| char_count | int | 分割品質の検証用 |
| source_engine | str | 採用エンジン（`plumber` / `pymupdf` / `mineru`）。突合の判定結果を痕跡として残す |

## 分割ルール

- 原則、最下層の条項単位で1チャンク
- 300字未満の条項は親階層でまとめる（断片化防止）
- 2,000字超の条項は項単位で分割し、hierarchyに枝番を付す
- 閾値（300字／2,000字）は仮置き。素材PDF確定後に実物で調整し、調整結果を改訂履歴に残す
- 表はMarkdown表としてbodyに保持。整形不能なら「表あり・p.XX参照」とだけ記す
- 帳票（v1.1）は表1枚＝1チャンク

## 評価レコード（検証ログ用・JSONL）

| フィールド | 内容 |
|---|---|
| question | 想定質問 |
| expected_source | 正解となる条番号 |
| retrieved | 検索で返ったchunk_id上位3件 |
| answer | LLMの回答 |
| verdict | pass / fail と一行の理由 |

- v1.1の帳票は評価対象外（抽出実演のみ）

## 設計判断の記録

- 埋め込み対象をbody単独でなくheading連結にした理由：条文本文だけでは「何についての規定か」が欠落し検索が外れやすいため
- source_engineを持たせた理由：複数エンジン突合の採用判定を検証可能な痕跡として残すため（検査業務の考え方の反映）
