## 3. 技術選定

| 技術 | 理由 |
|---|---|
| pdfplumber＋PyMuPDF突合 | 得意分野が補完的（罫線ベース表抽出／本文速度と読み順）。テキスト層PDFに対し誤読ゼロ |
| MinerU hybridバックエンド（v1.1） | CJKレイアウト解析の定番。VRAM 8GB要件をRTX 5060 Ti 16GBが充足。CPUフォールバック不要 |
| LlamaIndex | 検索主目的のRAGにおける定番。読み手への説明コストが低い |
| Chroma | ローカル・無料 |
| ruri-v3-310m | 日本語検索精度（JMTEB）で現行最良クラスのローカルモデル |
| Claude API | 生成層。キーは環境変数管理 |

## 4. 機能仕様

### §1 extract（突合抽出）
- 何を: 2エンジン（v1.1では3エンジン）で同一PDFを抽出し、arbiterが最良結果を採用する
- どのように: 判定基準は文字数のみに依存せず、文字化け率（U+FFFD・制御文字の出現率）と行断片化度を併用。採用エンジンと判定理由をログに残す
- 制約: 判定基準と閾値はREADMEに明文化する（検査業務の採用基準明文化の反映）

### §2 chunker
- 何を: データ定義v0.2の分割ルールを実装する
- どのように: 条番号の正規表現で階層を解析し、閾値ルール（300字／2,000字）で統合・分割
- 制約: 出力は中間JSONLとし、Chroma投入前に目視検査可能にする

### §3 ingest（埋め込み・格納）
- 何を: チャンクをruri-v3-310mで埋め込み、Chromaに格納する
- どのように: 埋め込み対象はheading＋body連結
- 制約: クエリ側／文書側プレフィックスはHuggingFaceモデルカードを正として実装時に照合し、付与漏れをユニットテストで検査する（付け忘れが最大の既知の罠のため。不確かな仕様を本書に書き写さない）

### §4 query
- 何を: 質問を受け、上位k件（既定3）を検索してClaude APIで回答生成する
- どのように: プロンプトに「出典の章・条番号を必ず明示、根拠がなければ『該当なし』と答える」を含める
- 制約: APIキーは環境変数。リポジトリに含めない

### §5 eval
- 何を: questions.jsonl 10問を一括実行し、results.jsonlを出力する
- どのように: retrieved上位3件・answer・verdictを記録
- 制約: pass判定は人間（ショウゴさん）が行う。検査の最終責任を機械に渡さない構成自体を展示する

### §6 MinerU拡張（v1.1）
- 何を: スキャン帳票1〜2枚をmineru.py経由でform型チャンク化し、検索に載ることを実演する
- どのように: MinerU hybridバックエンドで表構造をMarkdown/JSON抽出し、doc_type=formとして格納
- 制約: 10問評価は行わない。図面はスコープ外

## 5. テスト方針

| テスト対象 | 方法 | 合格条件 |
|---|---|---|
| 分割品質 | char_count分布と中間JSONLの目視 | 断片・巨大チャンクが説明可能な範囲に収まる |
| プレフィックス付与 | ユニットテスト | クエリ／文書両側に正しく付与されている |
| 全体（v1） | eval 10問 | 7問以上pass。未達分は失敗分析としてREADMEへ |
| v1.1 | 帳票1枚の実演 | 表構造がチャンク化され検索でヒットする |
